## Ответы на «вопросы себе»

**Почему middleware замера времени стоит ДО логирующего? Что будет, если после?**
Конвейер middleware выполняется по принципу «матрёшки»: каждый следующий
оборачивается в предыдущий. Middleware, стоящий раньше, охватывает своим замером
всё, что идёт после него. Поэтому `Stopwatch` ставим в начало — он измеряет полное
время обработки запроса (включая логирующий middleware и работу контроллера). Если
поставить его ПОСЛЕ логирующего, замер не учтёт время самого логирования и части
конвейера — измерение будет неполным.

> Практическое замечание: сам заголовок `X-Response-Time-ms` записывается через
> `Response.OnStarting(...)` — прямо перед отправкой ответа. Если писать заголовок
> уже после `await next()`, тело ответа часто оказывается отправленным, заголовки
> зафиксированы, и `Append` молча не срабатывает. `OnStarting` гарантирует запись.

**Почему сервис Singleton, а не Scoped? Что при перезапуске?**
`InMemoryTaskService` хранит задачи в поле `List<TaskItem>` в оперативной памяти.
- **Singleton** — один экземпляр на всё приложение. Список общий для всех запросов и
  всех пользователей, задачи «живут», пока работает процесс.
- **Scoped** создавал бы новый экземпляр (и новый пустой список) на каждый HTTP-запрос,
  поэтому созданные задачи исчезали бы сразу после ответа — задачник бы не работал.
- **При перезапуске приложения** данные теряются: память очищается, список пуст. Для
  постоянного хранения нужна БД (например, EF Core), а сервис тогда логично делать
  Scoped и хранить состояние в базе.

**Почему middleware `/health` не вызывает `next()`?**
Это «короткое замыкание» (short-circuit): middleware сам формирует ответ (200 + «healthy»)
и не передаёт запрос дальше по конвейеру — маршрутизация и контроллеры для `/health`
не выполняются. Так делают лёгкие health-check эндпоинты.

## Что сделано по шагам

- **Шаг 1.** Middleware: заголовок `X-App-Name: TaskBoard` + логирование `--> Method Path`
  и `<-- StatusCode`. Плюс усложнение: short-circuit `/health` → «healthy».
- **Шаг 2.** Middleware замера времени → заголовок `X-Response-Time-ms`.
- **Шаг 3.** `ITaskService` / `InMemoryTaskService` (CRUD в памяти), регистрация
  `AddSingleton<ITaskService, InMemoryTaskService>()`.
- **Шаг 4.** `TasksController`: `Index`, `Details`, `Create` (GET/POST), `Done`, `Delete`.
- **Шаг 5.** Razor-представления `Index` / `Details` / `Create`, пункт меню «Задачи».
- **Шаг 6.** JSON API: `ApiList`, `ApiGet`, `ApiCreate` + `CreateTaskRequest` (model binding
  из тела запроса через `[FromBody]`), ответы `Json(...)`, `CreatedAtAction(...)`, `BadRequest(...)`.
- **Шаг 7.** Проверка заголовков и запросов (через `curl`, эквивалент DevTools → Network).

## Дополнительные задания (на оценку 5)

**Уровень 1 (лёгкое).** Счётчик на странице `/tasks`: «Всего задач: X, выполнено: Y».
Считается в контроллере (`ViewBag.Total`, `ViewBag.Done`) и выводится во View.

**Уровень 2 (среднее).** Middleware проверки заголовка `X-Api-Key` для запросов к
`/tasks/api/*`. Без заголовка или при неверном значении → `401 Unauthorized`. С ключом
`secret123` API работает. Проверено: без ключа — 401, с ключом — 200/201.

**Уровень 3 (сложное).** Фильтрация `?status=all|done|active` на `/tasks`. Фильтр
применяется в контроллере, текущее значение сохраняется в ссылках фильтра и в скрытом
поле форм «выполнить»/«удалить», поэтому не сбрасывается при действиях над задачами.

## Вывод

Работа показала конвейер middleware ASP.NET Core (порядок регистрации = порядок
выполнения, «матрёшка»), внедрение зависимостей через встроенный DI-контейнер (и разницу
времён жизни Singleton/Scoped), классическую MVC-маршрутизацию с model binding, а также
отдачу как HTML (Razor), так и JSON из одного контроллера. В отличие от Web Forms из
работы №1, здесь нет ViewState и постбеков: состояние не хранится автоматически, работа
идёт через явные HTTP-запросы и маршруты.
